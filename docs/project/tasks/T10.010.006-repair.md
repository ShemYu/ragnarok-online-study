Root checks Claude ce9e7d64 against the frozen source and obtains an independent
Astra review. The main separate-save/direct-callback findings are useful, but
these corrections are required before selection:

1. **Carry-capacity example.** status_calc_weight uses base sd->status.str;
   ordinary equipment bStr changes a separate bonus field. STR gear alone
   does not establish the proposed capacity loss. A level-triggered forced
   unequip case needs an actually effective bAddMaxWeight item or another
   demonstrated carry contributor. Keep the case unproved if none is
   qualified. Cite status.cpp3717/3731 and pc.cpp SP_STR/SP_ADDMAXWEIGHT.
2. **Quest ACK ID mismatch.** The source passes char_id to the account-ID
   lookup. Without a matching account ID, the intended dirty flag stays set;
   a numerical collision may clear a matching session's flag, possibly
   another player's. Actual overlap is unknown. Do not say never clears,
   universally harmless/idempotent or assign severity without evidence.
3. **Possible persistence windows, not guaranteed outcomes.** W1 requires
   successful early D/pre-reward SQL persistence, no later reward save and
   interruption bypassing applicable save handlers. W2 needs persisted C
   plus some persisted rewards; with early saving enabled, a later quest
   failure does not undo an already persisted D. W3 partial rows do not stop
   the original in-memory reward; no new reward on a later held interaction
   is a different claim. State initial rows and successful/failed operations.
4. **Controlled interruption.** Timing alone does not prove the boundary.
   Require evidence of D/pre-reward DB state and absence of a later reward
   save. If a later save wins the race, classify boundary not captured; do
   not claim crash safety or guaranteed loss. Skip explicitly if that point
   cannot be safely controlled. Keep normal save/restart distinct.
5. **ACK and EXP scope.** A final ACK is queued before the following quest
   request is processed; that does not prove physical delivery or combined
   SQL success. Native rate/tax/cap reductions, including zero at a cap,
   are not automatic missing rewards: compare with a qualified oracle.
   Four million EXP alone cannot cross a4.7 million threshold from zero;
   state the required pre-existing EXP/remaining-threshold condition.

The smallest actual cases remain ordinary reward/save/reentry/repeat,

only if controllable. Runtime slots and installed schema remain unqualified.
