## Apply

1. **External admission.** Run
   `python3 -I -B tools/renewal/release_compatibility/release_gate.py --packet <abs packet>`.
   The packet's `roots.story` and `roots.text` are the exact two folders that
   step 3 selects. The gate takes a census of each: the five story files and
   the text folder's `mod.json` plus table, with nothing extra and no era or
   client override. Continue only on exit 0 with
   `"status": "admitted"`. Keep the JSON result and its gate, manifest and
   packet hashes privately. Any refusal stops the procedure. Fix the cause
   and re-qualify. Do not edit records to pass.
2. **Re-verify immediately before install.** The staged files to be selected
   must still equal the admitted pins. Re-run the gate if anything was
   touched.
3. **Supported folder installation, serially.** Use Install mod from folder
   for `tc-true-quest-text`, then for `ro-solo-ch1-entry`. After each one:
   - Inspect the returned message, including any refusal or "could not be
     switched on" note.
   - Inspect the mods listing and the exact installed file bytes.
   - Require the previous enabled set plus the two new mods, and every
     previous disabled choice.

   Remember that an app refusal can leave a folder installed and enabled. If
   that happens, stop and go to recovery. Do not copy live folders by hand.
4. **Full settings Apply, once.** Send `save_settings` with
   `{"settings":{}}` (the supported full apply). Mods Apply alone does not
   re-link client assets. Observe completion and any error. A resolved
   request or HTTP 200 alone is not sufficient.
5. **Generated and installed readbacks.** Each of these must match the
   admitted records:
   - The generated server import holds the three NPC files by hash and
     `db/import/quest_db.yml` with all four rows. No effective quest layer
     has `Clear`, and there is no unresolved collision.
   - A new native load uses the admitted executable and image, with no
     parser or table rejection. `ros_ch1_coin_capacity` is registered.
   - The three maps load, the three exits are present, and the asset server
     is back.
   - The generated text resource is byte-identical to the table.
   - The effective `customQuestInfo` array and order and `langtype: 4` equal
     the packet's expected values.
6. **Fresh-page text check.** Open a new normal verification page. Do not
   re-call `DB.lazyInit` and do not clear caches by hand. For each
   server-admitted quest:
   - Compare the Traditional Chinese title, summary and every description
     element with the reference hashes.
   - Include 18371 as soon as the verification character reaches it.

   This journal and rendering check is Root's separate post-apply gate. The
   pre-install gate does not prove it.
7. **Ordinary play.** On the verification character, check the
   starter/Messenger, travel and return, Shasha and Maysel (full-bag refusal
   and retry, plus matching-stack and new-stack rewards per .007), and
   save/re-entry. The user's short playtest follows only after Root's check.

## Failure recovery (fail closed, preserve progress)

- **Gate refusal:** nothing is installed. Keep the result and fix the
  cause.
- **Install refusal or partial enable, before any Apply:** keep the
  services as they are and do not Apply. Nothing new has been loaded. Remove
  only the folder this run just installed, using the app's supported Remove
  (which moves it to the trash). Then confirm the previous enabled and
  disabled set. Once an Apply has started, use the rule below instead.
- **Any failure after a full Apply has started** (Apply error, partial or
  failed load, readback mismatch, or a journal or play failure): Apply is not
  transactional. Assume the story may be partly loaded, and that a
  character may have travelled or recorded 18368–18371.
  - **Never disable the story package, and never leave it removed while
    anything could start.** Either would let the next load run without the
    four definitions and the three exits. The only removal allowed from this
    point on is the same-name replacement inside the
    [guarded offline sequence](#guarded-offline-same-name-replacement).
  - Read back the current state first.
  - If the current load keeps the four definitions and the exact exits, stop
    and hold for Root review.
  - Otherwise, replace the story with the pre-staged withdrawal source
    (prerequisite 6) using that guarded offline sequence.

  This applies even when it looks as if no character reached
  `ygg_edge`/`ygg_fruit`. That cannot be proven from outside each save.
- **Text-only failure** (the story readbacks pass): disable
  `tc-true-quest-text` alone, leaving the story with its definitions and
  exits, then do a full Apply,
  then open a fresh page. Confirm the resource and array entry are gone and
  the unrelated Chinese mods and settings remain. Never touch quest data to
  undo text.
- **Never as recovery:** quest deletion or reset, reward replay or
  compensation, a new marker, variable or transaction system, restoring an
  old save, or `Clear`. A partial or uncertain quest/reward tuple is held for
  explicit manual review (T10.010.006).

## Three separate contracts

Each folder that may be installed belongs to exactly one contract. One
contract's verification is never applied to another, and a pass under one
never transfers to a folder that differs from what it admitted.

| --- | --- | --- | --- |
| **Ordinary 0.3.2 release** | Story `ro-solo-ch1-entry` 0.3.2: exactly the five frozen files, **including all actors** (starter, Messenger, arrival, Shasha, Maysel, Est, Debris). The withdrawal contract is deterministic:

- `db/quest_db.yml` is the frozen four-row QUEST_DB file (517 B,

- `npc/connections.txt` is exactly `first_edge.txt` lines 129–138 (249 B,

- No consequential actor may appear anywhere in the folder.
- The new `mod.json`, executable, image, parser log, effective

  - every consequential actor checked, with none loaded.

The ordinary-release gate cannot admit these actor-free bytes, and a release
PASS is never reused for them. The withdrawal contract also refuses the
ordinary 0.3.2 folder.

**Preservation source.** A preservation source is the recovery folder
installed if a replacement fails. It is one of:

- the admitted withdrawal folder;
- the byte-identical admitted 0.3.2 release folder, admitted again by the
  release gate.

Both keep the four definitions and the three exits. Never use a modified
copy of either. Both the replacement input and the recovery input are
admitted, pinned and staged **before** any installed folder is removed.

## Guarded offline same-name replacement

Root source-reviewed these routes in the pinned app (`2c3b2612`), using
Root's packet copies of `electron/main.js` and `stack/src/cmds.rs`. They
explain why the order below matters:

- **Install from folder refuses an existing name.** `installModFrom`
  (main.js 1857–1891) throws `"<name> is already installed. Remove it
  first."`. Otherwise it copies the folder recursively with `fs.cpSync` and
  only then switches the mod on (`switchOnInstalled`, `mod-enable`). An
  enable failure is reported in the message, not thrown. `refusalNote` adds
  `It will not load: …`. A failed copy can therefore leave a partial folder,
  and a failed enable leaves the folder installed but off or refused.
- **`remove_mod({name, asked: true})`** (main.js 2470–2508) runs in this
  order:
  1. `shell.trashItem`. If this fails: "Nothing was removed".
  2. `mod-forget`. Its errors are only logged.
  3. `relinkForMods`. Its error propagates after the folder is already gone.

  Remove does not unload scripts from a running map server. `relinkForMods`
  (main.js 906–915) relinks client assets and restarts the asset server only
  if it was running. It does not start game services.
- **`stack_down`** is `runStack(['down'])` (main.js 2201), which reaches
  `down` (cmds.rs 2139–2178) and does the following, in order:
  1. Takes the stack lock.
  2. Stops the game services. If that fails, it leaves them running "to
     protect the save".
  3. Removes the containers.
  4. Stops the database within 30 s. If that fails, the VM is left running.
  5. Runs `nebula down` and waits for the engine to exit. If the engine has
     not exited within the budget, the call fails.
  6. Prints `stack down`.
- **Full Apply** is `save_settings` with `{"settings":{}}`. It is not
  transactional. Its asset-link step runs after the server `up`, so a late
  asset error does not prove the server failed.
- **Other handlers** used below:
  - `list_mods`: state, name and refusal reason per mod.
  - `stack_status`.
  - `install_mod({kind: "folder"})`. It takes no `src` parameter: the folder
    is chosen through the existing remote-dialog bridge, and no private
    installer shortcut is assumed.

### Sequence (Root only)

1. **Prequalify both inputs.** Each is pinned, admitted under its own
   contract, staged locally and owned exclusively:
   - the replacement folder;
   - the preservation source (see above).

   Re-run the matching gate on each just before step 3.
2. **Refresh the preconditions.**
   - Fresh ownership and user logout.
   - The supported current-state backup, taken while the stack can still
     run it.
   - A fresh isolated rehearsal of this exact Remove → Install → verify →
     Apply sequence with these exact folders. That rehearsal is the isolated
     recovery proof.
   - Snapshot `list_mods`: the enabled set, disabled set and refusal states.
3. **Graceful shutdown.** Call `stack_down`. Require success (`stack down`),
   then confirm actual departure with `stack_status` and no running game or
   database service. If it fails, **stop here and do not remove anything.**
4. **Exclusive offline ownership.** From here until step 8, nobody calls
   Apply, `start_stack`, `stack_up`, Start, or launches or reloads a game
   page. No other mod change is made. The app stays open only to serve these
   handlers.
5. **Remove.** Call `remove_mod({name: "ro-solo-ch1-entry", asked: true})`.
   Then check actual absence: no folder under the mods directory and no
   `list_mods` row.
6. **Install.** Call `install_mod({kind: "folder"})` and select the
   prequalified folder. Require `Installed ro-solo-ch1-entry.` with no
   "could not be switched on" or "will not load" note.
7. **Verify offline, before any start.** All of these must hold:
   - The complete installed bytes and file set equal the inventory admitted
     under the folder's own contract, with nothing extra.
   - The installed story folder holds all four definitions with no `Clear`,
     and the exact three-exit block.
   - **Withdrawal folder only:** no consequential actor is present. An
     ordinary 0.3.2 folder must instead contain all its admitted actor
     scripts unchanged.
   - `list_mods` shows the mod `on` and not refused.
   - Every unrelated enabled and disabled choice equals the snapshot.
8. **Only then, one full Apply.** Afterwards, check:
   - the generated import and a clean native load;
   - the four rows with no `Clear`;
   - the three exits effective and identical;
   - **withdrawal only:** no withdrawn actor loaded;
   - text array and settings as the contract expects.

   Play only after these checks pass.

### Failure branches

- **Shutdown fails (step 3):** stop before Remove. The services were left
  running by design. Inspect `stack_status` read-only and hold for Root.
- **Remove error (step 5):**
  - A `trashItem` failure means nothing was removed: stay offline and
    investigate.
  - Any later error (`mod-forget` or relink) means the folder may already be
    in the trash. Check actual presence. If it is absent, treat it as removed
    and continue with step 6, still offline.
  - A relink error alone does not show a server problem; the server is down.
- **Install error or partial result (step 6):**
  - "Already installed" means Remove did not take effect.
  - A copy error can leave a partial destination.
  - An enable or refusal note leaves the folder off or refused.

  In every case, stay offline. Shutdown has already succeeded, so the
  shutdown-failure stop rule does not apply here.
  1. Read the actual state: is the destination present, what is its
     inventory, and what is its `list_mods` row?
  2. If a partial or refused same-name destination exists, use the supported
     `remove_mod` on **only that failed destination**. Install from folder
     refuses an existing folder, so it cannot be installed over. If that
     Remove also errors, read the actual state again before acting (as in
     the Remove branch above).
  3. Verify actual absence: no folder and no row.
  4. Install the **prequalified preservation source** through Install from
     folder, and verify it against step 7 under its own contract.

  Until a source passes step 7, nothing is applied, started or launched. If
  no source can be verified, stay offline and escalate: a start would load
  without the definitions and exits.
- **Apply error (step 8):** Apply is not transactional.
  1. Inspect actual service state (`stack_status`) and the actual generated
     import and load, read-only.
  2. A late asset error alone does not prove the server failed.
  3. Before any further replacement, shut down gracefully again (step 3),
     then repeat steps 4–8 with the preservation source.
- **Never:** force removal, deleting files by hand outside the supported
  Remove, copying a folder manually, restoring an old save, `Clear`, or any
  Apply, start or launch while the folder is missing or partial. Every next
  admitted load contains all four definitions and the exact three exits.
