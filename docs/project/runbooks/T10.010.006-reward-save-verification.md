## 2. Oracle

- **EXP oracle:** compute B′/J′ from R1–R4, R8 and the analysis §3
  pipeline:
  `quest_exp_rate` → guild tax (base) → SC boosts → max-level clamp →
  `max_exp_gain_rate` → threshold consumption under the `multi_level_up`
  rule.
- The observable expectation is the final (level, remainder). It is **not**
  `old EXP + 65,304,744`.
- If any input is unknown, mark the numeric result UNKNOWN.
  - Native rate/tax/cap reductions, including zero at a max-level cap, are
    **not** a missing reward. Only a difference from the qualified oracle is
    a shortfall.
  - Without the oracle, record only: level did not decrease, and the
    observed values.

## 3. Cases (smallest set)

### C1 — ordinary reward, normal save, re-entry, repeat

- **Setup:** tuple (2,-1,1,-1). Pre-grant EXP chosen so no level-up occurs
  under R3, or base at max level with a cap explicitly computed. Free slot and
  weight margin. Record all observables (DB too).
- **Act:** complete Maysel's dialogue once. Then perform a normal logout
  (save point: `map_quit`) and log back in. Talk to Maysel twice, then to
  Shasha once.
- **Pass if all hold:**
  - tuple (2,-1,-1,1) in memory and DB;
  - coin count +10 in memory and DB;
  - DB `base_exp`/`job_exp`/levels equal the oracle;
  - repeat talks show `L_Onward` text;
  - coin count, EXP and tuple unchanged after the repeats;
  - no `ROSOLO_CH1` hold or warning line.
- **Refuse if:**
  - any reward is duplicated;
  - the DB differs from memory after logout;
  - the tuple is not 7 after re-entry.
- **Unknown:** the EXP equality, while R2/R3/R8 are unqualified.

### C2 — justified level-up and callback case

- **Justification:** source shows level-up runs `status_calc_pc`, possible
  `elvmax` unequip, direct item scripts and queued level-up events inside the
  reward window.
- **Setup:** a disposable character whose qualified pre-grant EXP satisfies
  `pre-existing EXP ≥ threshold − J′` (or `− B′`) under R3, i.e.
  remaining-to-threshold ≤ the effective gain. Example (source-default 4th
  job, JobLv1→2 = 4,700,000; not effective): J′ = 4,000,000 needs
  ≥ 700,000 pre-existing job EXP. Four million from zero does not level.
  - **Variant a:** no `elvmax` gear and a weight margin of at least the coin
    weight ×10 plus slack.
  - **Optional variant b (carry):** equip one `elvmax == current level`
    item that R4 qualifies as an **effective `bAddMaxWeight`** (or other
    demonstrated carry) contributor. Set the weight so the coins fit only
    with that contribution. A STR-bonus item does **not** qualify, because
    `bStr` does not enter max weight. If no such item is qualified, record
    variant b as *not run, unproved*.
- **Act:** complete Maysel once, then press close.
- **Pass (a) if:**
  - final level/remainder match the oracle;
  - coin +10 and tuple 7;
  - every R5 level-up handler shows its own observable effect after
    Maysel's state ended (after the close). No fixed delay is expected:
    timers may be armed earlier and re-queue while Maysel is attached;
  - no handler effect is observed between preflight and `getitem`;
  - no `event queue is full` or `event timer is full` warning appears.
    The absence of a warning is supporting evidence only; the handler
    effects are what is judged.
- **Variant b:** either coin +10, or `L_RewardHold` text plus a
  `buildin_getitem: Failed` line with tuple 7 and coins unchanged. The
  latter is an **expected-refusal outcome to record**, not a pass of reward
  delivery. It then goes to §4 review.
- **Refuse if:**
  - level or remainder differ from the oracle;
  - a handler is silently missing;
  - a `Double continuation` or lost-state line appears.

## 4. Manual-review procedure (uncertain or held reward)

Triggers:

- an `L_RewardHold` text, or a `ROSOLO_CH1: reward readback … held, no
  replay.` line;
- an `L_Hold`/`L_Conflict`/`L_Interrupted` line;
- a C4-type observation;
- a player report of missing coins with tuple 7, or EXP that differs from
  the qualified oracle (a native reduction or cap alone is not a trigger).

1. **Freeze, do not repair.**
   - Do not replay the dialogue, reset quests, restore an old save or
     re-grant.
   - The story keeps no permanent marker. The next Maysel talk at tuple 7
     shows `L_Onward`, which is safe because it grants nothing.
   - The warning is **not durable quarantine**.
2. **Capture evidence read-only** for that char ID:
   - the log lines (with time);
   - memory observables if still online;
   - DB rows from §1 after a confirmed save point (logout).
   - Record which of these exist: the pre-grant snapshot (if any), the coin
     count before (`.@coin` printed in the debugmes) and after.
3. **Classify:**
   - **coins:** delta 0 or 10;
   - **EXP:** matches the oracle, partial, or 0. Without a pre-grant
     snapshot, EXP is **unknown**;
   - **tuple:** 7 / 6 / 5 / 3.
4. **Decide with the user.** Unrelated progress (other quests, items, levels
   gained since) must be preserved.
   - Any compensation is a separate, explicitly approved, single manual
     action on the live character (for example a GM grant of the exact
     missing amount), recorded with before/after DB rows.
   - Never use a whole-character or old-save restore.
   - If the tuple is 6 and rewards are present (duplicate risk), escalate
     before the character talks to Maysel again.
5. **Record** the case in the task evidence with redacted IDs.
