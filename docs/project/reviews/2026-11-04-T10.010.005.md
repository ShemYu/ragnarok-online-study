## Design summary

The design is detailed in the
[gate README](../../../tools/renewal/release_compatibility/README.md).

- **External gate outside the app.** The app's `requires` only accepts
  `app`, `era`, `mods` and `client`. The gate refuses any other key in
  either staged manifest. No native-capability key is invented.
- **Explicit inputs and safe reads.** The packet names every input
  explicitly. The gate accepts no unknown role and does no discovery.
- **Every input is checked before use.** Each path must be absolute and
  normalized, with no symlink in any component. Each file must be regular,
  have `nlink 1` and be opened with `O_NOFOLLOW`. Its identity is rechecked
  after opening, its size is capped, and it must match both its packet pin
  and its manifest pin.
- **Bounded output, no writes.** Output is one JSON result on stdout, with at
  most 64 reasons and the hashes of all inputs. The gate writes nothing.
- **Real versus synthetic mode.**
  - Real mode only uses the bundled manifest. It refuses synthetic
    manifests, packets and records.
  - Real mode refuses while any runtime pin is `null`: executable, stock
    executable, image, ABI or effective configuration.
  - Synthetic mode can at best report `synthetic_consistent`, which is never
    an admission.
- **Native evidence must agree.** These must all describe the same supplied
  executable and staged script and DB bytes, the same image and
  configuration, and app commit/tree `2c3b2612…`/`8cab4674…`:
  - an isolated runtime qualification;
  - a pinned raw parser log;
  - a builtin registration plus probe observations (fits 1, no-fit 0);
  - a stock control that rejects the release;
  - `linux/arm64` and packet 20221005.

  A host fixture, a label or a bare boolean does not qualify.
- **Effective facts.** Required facts:
  - Two independent alias resolutions, both giving 1001972.
  - Etc, weight 1, stackable, non-GUID and non-pet.
  - Actual stack restrictions and `max_amount`, which must equal the native
    record. There is no 30000 default.
  - Three loaded maps and the three exits.
  - The three NPC imports by hash, each exactly once.
  - Four effective quest rows with the pinned Title hashes.
  - No `Clear` layer and no unresolved collision.
- **Text.** Required:
  - The staged table pin, which must also be the generated resource.
  - The exact selected server and full ordered `customQuestInfo` from the
    packet.
  - `langtype 4`.
  - Diagnostics scoped exactly to 18368–18371.
  - A complete full-reference packet. Its Title and Summary must equal the
    four frozen public hashes, and it must have non-empty Description
    element hashes for all four IDs.

  No Description hash is invented in the manifest.
- **Separate runbook.** The new 0.3.2 runbook covers:
  - fresh ownership, logout, backup and isolation;
  - admission before serial folder installation;
  - one full settings Apply;
  - generated and installed readbacks and the fresh-page text check;
  - fail-closed recovery.

  Withdrawal keeps all four definitions without `Clear`, plus the exact
  first_edge lines 129–138 (249 B, `e315e146…`). It removes consequential
  actors only through a separately reviewed withdrawal source. Progress is
  kept, with no reset, replay, marker or old-save restore.

  tell whether an `actual` record is true. Root establishes the runtime
  facts, and Root's pinning of the manifest is the trust anchor.
- The parser-log marker screen is heuristic. It may need Root's actual log
  format.
- The record schemas are this candidate's proposal. Root may adjust field
  names when the .004 outputs exist. The manifest's runtime slots stay `null`
  until then.
- The `prepared_source_tree_sha256` binding uses Root's recorded fresh
  reconstruction value `b64e850b…`. If the recipe's tree definition changes,
  Root revises the manifest.
- The synthetic Description hashes are labelled placeholders. No real
  Description, translation or raw asset text was used or published.
- The withdrawal source is described, not produced. The brief forbids story
  production edits here.
- Nothing was installed, applied, restarted, backed up or restored. No
  Engine, VM, browser, network, SQL or service action was taken.

### Runbook

- **Contracts.** A new "Three separate contracts" section covers:
  - **Ordinary 0.3.2 release:** full scripts including actors; actor-absence
    checks are not applied.
  - **Text-only replacement:** the text folder holds only its `mod.json` and
    resource. The installed story folder keeps the four definitions and the
    three exits.
  - **Actor-free withdrawal/preservation:** the separate contract above.
- **Preservation source:** either the admitted withdrawal folder, or the
  byte-identical admitted 0.3.2 folder re-admitted by the release gate.
  Never a modified copy. Both the replacement and the recovery input are
  qualified before removal.
- **Guarded offline same-name replacement.** This is source-reviewed from
  pinned `main.js` 1857–1891, 2201, 2431–2439, 2470–2508 and 906–915, and
  from `cmds.rs` 2139–2178:
  1. Prequalify and re-gate both inputs.
  2. Refresh ownership and logout, the backup, an isolated rehearsal and a
     `list_mods` snapshot.
  3. `stack_down`, then confirm actual departure.
  4. Hold exclusive offline ownership.
  5. `remove_mod({name, asked: true})`, then check actual absence.
  6. `install_mod({kind: "folder"})` through the existing dialog bridge.
  7. Verify the complete bytes, contract-specific actors, the four rows and
     three exits, on/not refused, and unrelated choices unchanged.
  8. Only then a full Apply (`save_settings({settings:{}})`) and the
     effective checks.

  Nothing is applied, started or launched while the folder is missing,
  partial or unverified.
- **Failure branches:**
  - Shutdown failure stops before Remove.
  - After a Remove or relink error, read the actual state first; the folder
    may already be in the trash.
  - After a copy or enable failure, stay offline and inspect. Supported
    Remove of **only that failed destination**, then verify absence, then
    install the preservation source and verify it.
  - After an Apply error, inspect the actual services and load, and shut down
    gracefully before any further replacement. A late asset error does not
    prove the server failed.
  - Never force removal or restore an old save. Every next admitted load
    keeps the four definitions and three exits.
