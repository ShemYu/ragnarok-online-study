## Defects and fixes

### 1. Worker completion accepted without actual-time evidence

Before: `classifyMap` trusted the absence of a delivered timer callback. An
otherwise successful record with `elapsed_ms` 55001 against an effective limit
of 55000 returned `observed`. `elapsed_ms` was also taken at `exit`, before the
stdout/stderr streams drained.

After (`runMapWorker`):

- `effective_deadline_ms` is fixed at launch as
  `min(worker_deadline_ms, remaining whole-run time)` and recorded.
- `exit_elapsed_ms` is recorded at `exit`. The deadline timer keeps running
  until both worker streams emit `end`. `elapsed_ms` is measured at that final
  settle point, from launch through exit and drain. `streams_drained` records
  whether both streams ended.
- If the deadline passes after exit with a stream still open, the record
  settles as undrained instead of hanging.

After (`classifyMap`): a host failure is recorded when `elapsed_ms` or
`effective_deadline_ms` is missing, non-finite or negative. It is also recorded
when `elapsed_ms > effective_deadline_ms` or `streams_drained !== true`. A timer
callback is not required for an overrun to fail.

### 2. Whole-run deadline not enforced after final postchecks or publication

Before: the run timer was cleared before the final synchronous postchecks. It
only interrupts a running worker. A pilot whose final profile posthash stalled
for 2500 ms under a 2000 ms cap finished with `elapsed_ms` 2614.793 and was
still `observed`.

After (`execute`):

- `manifest.run_deadline.after_postchecks` records actual elapsed time against
  `all_run_deadline_ms` after the final postchecks and before the manifest is
  built. An overrun adds a `run-deadline` error, so the manifest status is
  `failed`.
- After `MANIFEST.json` is written (exclusive, fsynced), actual time is checked
  again. If publication finished late, the run returns `failed` and writes one
  extra exclusive `RUN_DEADLINE.json` (mode 0600, counted against the retained
  cap). The manifest is never rewritten, so its exclusive semantics are kept.
- The CLI already exits 1 for any non-`observed` status, so either overrun
  gives a nonzero completion.

An on-time run writes no `RUN_DEADLINE.json`. Its only addition is the
`run_deadline` field in the manifest plus the new lifecycle timing fields in
each map report.

## Limits

- Synthetic controls only. Real prefix/suffix/body behavior, real timing and
  the CLI path with the real pinned profile are not exercised. All real
  execution remains Root-owned under separate admission.
- No end-to-end test makes a real worker finish after its deadline while its
  timer callback is never delivered. That path is covered by the pure
  classifier rows and by recording drain-inclusive elapsed time from real
  synthetic workers.
- The undrained-after-exit settle path (a stream never ends) is not reproduced
  with a real worker. It is covered only at the classifier level.
- A late publication leaves an on-time-looking `MANIFEST.json` (`observed`)
  next to the authoritative `RUN_DEADLINE.json` and the nonzero result. Readers
  must treat any `RUN_DEADLINE.json` as overriding the manifest status.
- Time between the publication check and process exit (result serialization,
  stdout write) is not separately bounded.
- The time measurement uses the parent's `performance.now()`. It is not an
  adversarial or wall-clock guarantee.
