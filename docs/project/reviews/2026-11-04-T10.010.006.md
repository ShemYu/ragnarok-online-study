### Queued versus direct execution

- **Queued:** `npc_script_event` (P:src/map/npc.cpp:6007–6020) calls
  `npc_event_sub` per registered `OnPCBaseLvUpEvent`/`OnPCJobLvUpEvent`
  handler. While `sd->npc_id != 0` (set by `script_attach_state`,
  P:src/map/script.cpp:4365), each event is **enqueued** (npc.cpp:1821–1833).
  The queue has **2 slots** (`MAX_EVENTQUEUE`, P:src/map/map.hpp:73). Beyond
  that, events are **dropped** with only a warning (npc.cpp:1832).
  - **Dequeue:** `npc_event_dequeue` arms a 100 ms event timer for the
    queue head and shifts the queue (npc.cpp:1245–1274). If no timer slot is
    free, the head stays queued (1265–1269).
  - **Not only at Maysel's END:** any script state that reaches END without
    a backup state also dequeues (script.cpp:4323–4334). A direct
    achievement condition is one such case (see below). So a timer may be
    armed **before** Maysel ends, possibly while `close2` waits.
  - **Timer fires while Maysel is attached:** `pc_eventtimer` → `npc_event`
    → `npc_event_sub` (pc.cpp:11789–11808; npc.cpp:1868–1895, 1821–1861).
    With `sd->npc_id` set, it **re-enqueues** the event, where it can again
    be dropped if the 2 slots are full.
  - **Supported conclusion:** a timer never runs inside the synchronous
    reward pass, so no queued handler executes between preflight and
    `getitem`. Handler execution needs Maysel's state to have ended, and its
    start time is not a fixed offset from Maysel's END.

  The same queuing applies to `NPCE_LOGOUT` raised by `map_quit`
  (P:src/map/map.cpp:2283).
- **Direct (synchronous re-entry into the script engine inside the window):**
  - `status_calc_pc_` runs item `script`/`equip_script`, combo, SC and pet
    bonus scripts via `run_script(..., sd->id, 0)`
    (P:src/map/status.cpp:3976–4264), then re-attaches the previous state
    (5051–5066).
  - `pc_unequipitem_sub` runs `unequip_script` with a fake NPC
    (P:src/map/pc.cpp:12413–12470).
  - Achievement condition scripts run directly in
    `achievement_check_condition` (P:src/map/achievement.cpp:875–908). It
    **explicitly detaches** Maysel first (`script_detach_rid`, which also
    clears `rid`; script.cpp:13439–13446). It then runs the condition, frees
    the condition state, restores `rid` and re-attaches Maysel (897–903).

  For the status and unequip paths, the nested `run_script` backs Maysel's
  state up as `bk_st`. It restores it on detach **without** dequeuing
  (script.cpp:4306–4320, 4350–4370).

  The achievement path is different. The condition state has no `bk_st`, so
  on END it takes the dequeue branch (4323–4334) and may arm a level-up event
  timer that is already queued. That is the case when this runs from
  `pc_checkbaselevelup` after `NPCE_BASELVUP` was enqueued (pc.cpp:8354,
  8360–8362).

  **No dialogue yield does not mean no re-entry.** Direct callbacks (inside
  the pass) and queued NPC handlers (only after Maysel ends) remain distinct
  mechanisms.

### What can invalidate capacity or attachment between preflight and getitem

1. **Max weight (conditional; unproved).** `status_calc_weight` sets
   `max_weight = job max weight + sd->status.str * 300`
   (P:src/map/status.cpp:3717). That is the **base** STR stat. Ordinary
   equipment `bStr` is applied by `pc_bonus` `case SP_STR` to the separate
   `indexed_bonus.param_bonus[]` (P:src/map/pc.cpp:3764–3772), so it does not
   enter this formula. **Losing STR gear alone does not reduce carry
   capacity.**

   Contributors this source does show are:
   - `bAddMaxWeight` (`case SP_ADDMAXWEIGHT` → `sd->add_max_weight`,
     pc.cpp:4474–4476), added at status.cpp:3731;
   - carry skills, riding/dragon/Madogear and `SC_KNOWLEDGE`
     (status.cpp:3732–3744).

   A capacity loss between preflight and getitem therefore needs a
   level-triggered `elvmax` forced unequip (pc.cpp:8371–8372) of an item that
   is **effectively** a `bAddMaxWeight` (or other demonstrated carry)
   contributor, or a direct script that changes such a contributor or the
   inventory. No such item or script is qualified. The case stays
   **unproved**. Gaining a level does not change base STR, because status
   points are not auto-spent. Slots and stacks change only if a direct script
   adds or removes items.
2. **Attachment.** A nested direct script that yields (`mes`/`next`/`sleep`)
   would leave Maysel's state displaced. This is the "double continuation" or
   lost-state path in script.cpp:4482–4502. Achievement conditions also
   detach and re-attach Maysel explicitly, and their END may arm an event
   timer as described above. The outcome depends on the effective item and
   achievement scripts, which are **not assessed**.
3. **Unobserved EXP result.** No error or story branch reports
   `pc_gainexp` early returns, the max-level clamp (possibly zero), tax or
   caps. These are native configured behaviour; only a difference from a
   qualified oracle is a shortfall (G1).
4. **Quest state.** Only `changequest` mutates it. The in-memory readback is
   exact, but it proves **memory**, not persistence.

3. registry if dirty;
4. **status 0x2b01** (whole `mmo_charstatus`, including level/EXP; 326–333);

7. achievements.

### What is and is not established

- **Request order** within one `chrif_save` is fixed: inventory → status →
  quest. The char-server processes the link in order. Across saves, the
  changequest-triggered save precedes every reward save.
- **Successful normal save** cannot be observed through any ACK. Status has
  none, inventory/quest ACKs only produce log lines, and a queued 0x2b21
  ignores SQL errors. It must be established by reading the database after a
  save point.
- **Restart persistence** equals whatever SQL rows exist at reload
  (`mapif_quests_fromsql`, int_quest.cpp:26–70; inventory/status loaders).
- **Crash atomicity: none in source.** The windows below are **possible**
  outcomes under stated prerequisites, not guaranteed results.
  - Notation: C = 18370 active (tuple 6), D = 18371 active (tuple 7).
  - Initial rows for all three: quest {18368:2, 18370:1}, no 18371; `char`
    holds pre-reward levels/EXP; `inventory` holds the pre-reward coin
    amount (possibly none).

  - **W1: D persisted, rewards not persisted.** All of these must hold:
    - (a) `save_settings & CHARSAVE_QUEST` is effective;
    - (b) the char link was up, so the `changequest` save was actually sent
      (chrif.cpp:301);
    - (c) its quest SQL succeeded for both `INSERT 18371` and
      `DELETE 18370`, and the pre-reward status `UPDATE` either succeeded or
      is irrelevant;
    - (d) **no later save carrying the rewards was processed successfully**
      before the interruption: no autosave, logout, map-server change or
      other `CSAVE_INVENTORY` save, and no status save for EXP;
    - (e) the interruption bypassed or defeated every applicable save handler:
      `map_quit`/finalize (map.cpp:2355, 5087) and the crash-signal handler
      (map.cpp:5200–5215), which saves only if the link is up.

    Then the restart rows show D with pre-reward EXP/coins, and Maysel takes
    `L_Onward` with no `ROSOLO_CH1` line. If a later reward save did succeed,
    the rewards persist. If (c) fails, see W2/W3.

    Evidence limit for (d):
    - DB snapshots show only the persisted states at those moments.
    - Absent log lines do not show that no save was attempted.
      `pc_autosave` logs nothing per character (pc.cpp:13104–13141), and
      inventory and quest saves log only failures.
    - Claiming (d) as a boundary needs an independently qualified
      observation method. None is qualified (see runbook C4).
  - **W2: C persisted plus some rewards persisted.** This needs **all** of:
    - (a) the restart rows still show C (18370 row present, 18371 absent);
    - (b) at least one reward row persisted: inventory coin rows and/or
      `char` EXP/levels.

    Possible paths:
    - `CHARSAVE_QUEST` off, and a later combined save processed inventory
      (and/or status) before its quest request, then stopped or failed;
    - with `CHARSAVE_QUEST` on: the early quest save was **not** persisted
      (link down so nothing was sent, or both quest statements failed), and a
      later save then persisted reward rows but not the quest change.

    **With early saving enabled, once D has persisted, a later quest-save
    failure does not undo it.** The diff runs against SQL rows that already
    hold D (int_quest.cpp:139–163). Under W2 the restart tuple is 6, so
    Maysel's flow would run its preflight and could grant again on top of the
    persisted rewards.
  - **W3: partial quest rows.** `INSERT 18371` precedes `DELETE 18370`
    (int_quest.cpp:157, 162), and failures are not rolled back.
    - Insert OK, delete failed → rows (2,-1,1,1) = state 3.
    - Insert failed, delete OK → rows (2,-1,-1,-1) = state 5 (entry
      `L_Interrupted`, S:npc/entry.txt:171).

    These SQL rows **do not stop the original in-memory reward**. That
    session still reads tuple 7 in memory, so `getexp`/`getitem` already ran.
    Later saves resend the quest log while `save_quest` stays set (see D1)
    and may converge the rows. W3 persists to a restart only if no later quest
    save succeeds. The reward rows persist or not independently, per the
    reward saves. After a restart in state 3 or 5, the story grants **no new**
    reward on the held interaction. That is a separate claim from whether the
    original reward persisted.

### Source-established defects and gaps (report only; nothing edited)

- **D1 (native ID mismatch; severity not assigned):** `intif_parse_questsave`
  passes the packet's **char ID** to `map_id2sd(cid)`
  (P:src/map/intif.cpp:2120–2127). `pc_db` is keyed by `sd->id`, which is the
  account ID (P:src/map/map.cpp:2190, 2363–2366; P:src/map/pc.cpp:1452).
  The outcome is conditional:
  - **No online session has account ID == that char ID:** the lookup returns
    null. The intended clear of the saving player's `save_quest` does not
    happen. The flag stays set, and later `chrif_save` calls resend that
    player's quest log (chrif.cpp:346–347).
  - **A numerical collision** (some online session's account ID equals the
    char ID): that session's `save_quest` is cleared, and it may be another
    player's. If that session had unsent quest changes, they would not be
    resent until its next quest mutation sets the flag again.

  Actual ID-range overlap in the installed data is **unknown**. The source
  default `char` AUTO_INCREMENT is 150000 (P:sql-files/main.sql:296); account
  ranges are not established here. No claim is made that the flag is never
  cleared, that resends are always harmless, or how severe this is. Either
  way, the quest ACK confirms nothing to the saving session beyond the
  absence of an error line. Whether the line is upstream or app-modified is
  not determined (`intif.cpp` is in the modified footprint).
- **G1 (story observability, not a native defect):** EXP is neither read back
  nor branch-checked, and `getexp`/`pc_gainexp` give no status. Native
  reductions are configured behaviour, **not automatically missing rewards**:
  - quest rate;
  - guild tax;
  - `max_exp_gain_rate`;
  - the max-level clamp, including **zero gain at a cap**;
  - early returns when off-map, dead, or on PvP without `pvp_exp`.

  A shortfall exists only when the observed result differs from a qualified
  oracle (§3).
- **G2:** a `getitem` refusal reaches `L_RewardHold`, while D may already be
  persisted (W1 prerequisites (a)–(c)). The hold is a warning plus a
  `debugmes` line, not durable quarantine. The next talk takes `L_Onward`
  (state 7) with no marker.

## 3. Conditional EXP expectation

The pipeline for the argument pair (B, J) = (65,304,744, 4,000,000) is below.
**Monster `base_exp_rate`/`job_exp_rate` are not applied on this path.**

1. `B1 = min(floor(B * quest_exp_rate/100), MAX_EXP)`, and the same for J
   (script.cpp:11266–11271). The default rate is 100
   (P:conf/battle/exp.conf). `MAX_EXP` depends on PACKETVER
   (P:src/config/const.hpp:64–68).
2. Guild tax on base only: `B2 = B1 - floor(B1 * exp_mode/100)` when the
   character is in a guild with position `exp_mode ≥ 1`
   (P:src/map/guild.cpp `guild_payexp`); 100 or more takes all.
3. Boosts with `src = nullptr`, so race/class/VIP-monster bonuses do not
   apply. They are `SC_EXPBOOST` (+VIP battle-manual share) and
   `SC_PERIOD_PLUSEXP_2ND` for base. Job gets `SC_JEXPBOOST` plus the same
   **accumulated** bonus (pc.cpp:8453–8478). Note the base bonus total also
   carries into the job calculation. Each result is clamped to [1, MAX_EXP].
4. Max level: at max base/job level, gain is limited so the total stays
   ≤ 99,999,999 base / 999,999,999 job (pc.cpp:8543–8554; const.hpp:73–75).
5. `max_exp_gain_rate` (default 0 = off) caps gain to a fraction of the
   current next-level requirement (8556–8569).
6. Level consumption (pc.cpp:8305–8327, 8378–8401) works in two cases:
   - `multi_level_up` off (default): each loop subtracts the threshold and
     caps the remainder at `threshold-1`. The loop continues only while the
     remainder still meets the **next** threshold, so a non-monotonic table
     could still allow more than one level.
   - `multi_level_up` on: unlimited levels up to `multi_level_up_base/job`.
   The observable EXP field is the **post-consumption remainder**, never
   `old + B`.
7. Base and job are independent. Base level-up handlers are queued before job
   EXP is added.

Source-default tables, `P:db/re/job_exp.yml`, labelled **authored/default,
not effective**:

- **3rd classes:** max base 200 (lines 573–640, 1038–1040). A Lv200 3rd class
  is at max, so base gain clamps toward 99,999,999. A large stored base EXP
  can make it 0.
- **4th classes:** max base 275. Lv200→201 needs 653,047,446 (1468), and
  B is about 10.0% of that. A base level-up needs pre-existing base EXP
  ≥ 653,047,446 − B′, where B′ is the effective gain after rate, tax, boosts
  and caps. With an unmodified B′ = B that is ≥ 587,742,702.
- **4th-class job (block 2789):** JobLv1→2 needs 4,700,000. Four million
  from zero **cannot** cross it. A job level-up needs pre-existing job EXP
  ≥ 4,700,000 − J′, i.e. ≥ 700,000 if J′ = 4,000,000 unmodified; more if
  J′ is reduced, less if boosted. Equivalently, the remaining-to-threshold
  amount must be ≤ J′. 3rd-class job is max 70; at max, job gain clamps so
  the total stays ≤ 999,999,999, possibly to zero.

   weight/stack in the
   effective item DB, current weight/max weight, inventory slots and coin
   stack.
7. Registered `OnPCBaseLvUpEvent`/`OnPCJobLvUpEvent` handlers and whether the
   2-slot event queue is free.
8. Effective `save_settings`, `autosave_time`, `minsave_time`, schema engine
   and server log path.

Without items 1–5 no numeric expectation is valid. The gain may be reduced
(even to 0 at a cap) or boosted, and only the qualified oracle decides
whether a result is correct. A level change is expected only when the
threshold arithmetic with qualified pre-grant EXP says so.

## Limitations

- This is source reading only. Effective configuration, database, item
  scripts, NPC handlers, schema and binary are unknown, and no runtime
  behaviour is proven.
- Item, achievement and SC scripts in the effective DB were not audited for
  yields or inventory changes; the attachment risk stays conditional.
- The upstream-versus-app origin of D1 was not determined, nor whether any
  installed char ID equals an online account ID.
- No effective `bAddMaxWeight`/carry item is qualified, so the carry-loss
  case is unproved.
- W1–W3 are conditional windows. None is observed, and none is a
  guaranteed outcome.
- The patched capacity function was read from the pinned patch; the eventual
  patched binary must be qualified separately.
