### Queued versus direct execution

- **Queued:** `npc_script_event` (P:src/map/npc.cpp:6007–6020) calls
  `npc_event_sub` per registered `OnPCBaseLvUpEvent`/`OnPCJobLvUpEvent`
  handler. While `sd->npc_id != 0` (set by `script_attach_state`,
  P:src/map/script.cpp:4365), each event is **enqueued** (npc.cpp:1821–1833).
  The queue has **2 slots** (`MAX_EVENTQUEUE`, P:src/map/map.hpp:73). Beyond
  that, events are **dropped** with only a warning (npc.cpp:1832). Queued
  events start ≥100 ms after Maysel's state ends (`npc_event_dequeue` →
  `pc_addeventtimer`, npc.cpp:1245–1274; `pc_eventtimer`, pc.cpp:11789). That
  is after the close click, not before `getitem`. The same queuing applies to
  `NPCE_LOGOUT` raised by `map_quit` (P:src/map/map.cpp:2283).
- **Direct (synchronous re-entry into the script engine inside the window):**
  - `status_calc_pc_` runs item `script`/`equip_script`, combo, SC and pet
    bonus scripts via `run_script(..., sd->id, 0)`
    (P:src/map/status.cpp:3976–4264), then re-attaches the previous state
    (5051–5066).
  - `pc_unequipitem_sub` runs `unequip_script` with a fake NPC
    (P:src/map/pc.cpp:12413–12470).
  - Achievement condition scripts run directly
    (P:src/map/achievement.cpp:875–885).

  Each nested `run_script` backs up Maysel's state as `bk_st` and restores it
  on detach without dequeuing (script.cpp:4306–4320, 4350–4370). **No dialogue
  yield does not mean no re-entry.**

### What can invalidate capacity or attachment between preflight and getitem

1. **Max weight.** `max_weight` is recomputed from job base weight, STR×300
   and bonuses on every status calculation (P:src/map/status.cpp:3717–3743).
   A level-up that unequips `elvmax` gear (pc.cpp:8371–8372), or direct
   item/SC scripts that lower STR or weight bonuses, can turn the preflight's
   1 into `ADDITEM_OVERWEIGHT` at getitem. Gaining a level alone does not
   change STR. Slots and stacks change only if a direct script adds or removes
   items.
2. **Attachment.** A nested direct script that yields (`mes`/`next`/`sleep`)
   would leave Maysel's state displaced. This is the "double continuation" or
   lost-state path in script.cpp:4482–4502. It depends on the effective item
   and achievement scripts, which are **not assessed**.
3. **Silent EXP no-op.** No observable error or story branch exists for
   `pc_gainexp` returning early, the max-level clamp or guild tax.
4. **Quest state.** Only `changequest` mutates it. The in-memory readback is
   exact, but it proves **memory**, not persistence.

## 2. Save and acknowledgement timeline

### Requests

`chrif_save` (P:src/map/chrif.cpp:277–352) runs `pc_makesavestatus` (282). It
then **returns -1 without sending anything if the char-server link is down**
(301; macro at 124). The caller ignores this, and the comment says "saved on
reconnect" (`chrif_on_ready`, 549–558). Otherwise it queues, on the single
shared link (`inter_fd` = `char_fd`, P:src/map/intif.cpp:53), in this order:

1. storage if dirty;
2. **inventory 0x308b only with `CSAVE_INVENTORY`** (307–308); cart;
3. registry if dirty;
4. **status 0x2b01** (whole `mmo_charstatus`, including level/EXP; 326–333);
5. pet/homunculus/mercenary/elemental;
6. **quest log 0x3061 if `save_quest`** (346–347);
7. achievements.

| Trigger | Flags | Persists |
| --- | --- | --- |
| `changequest` with `CHARSAVE_QUEST` (P:src/map/map.hpp:1138; default `save_settings: 4095`, P:conf/map_athena.conf:114) | `CSAVE_NORMAL` | status **before EXP**, quest log with 18371. **Not inventory.** |
| `getexp`, level-up, `getitem` | none | nothing; memory only |
| autosave (P:src/map/pc.cpp:13104–13141) | `INVENTORY\|CART` | inventory, status, quest log. One character per tick. Interval is `autosave_time*1000/(users+1)`, min `minsave_time` (defaults 300 s / 100 ms). The single-user round-robin saves about every second tick. |
| normal logout `map_quit` (P:src/map/map.cpp:2236–2357) | `QUIT\|INVENTORY\|CART` (2355) | everything above, char set offline |
| graceful shutdown (map.cpp:5087) | via `map_quit` | same |
| crash signal (map.cpp:5200–5215) | best effort, only if the link is up | same; nothing on SIGKILL or power loss |

### What is and is not established

- **Request order** within one `chrif_save` is fixed: inventory → status →
  quest. The char-server processes the link in order. Across saves, the
  changequest-triggered save precedes every reward save.
- **Successful normal save** cannot be observed through any ACK. Status has
  none, inventory/quest ACKs only produce log lines, and 0x2b21 ignores SQL
  errors. It must be established by reading the database after a save point.
- **Restart persistence** equals whatever SQL rows exist at reload
  (`mapif_quests_fromsql`, int_quest.cpp:26–70; inventory/status loaders).
- **Crash atomicity: none.** The source establishes these windows:
  - **W1 (default `CHARSAVE_QUEST`):** 18371 is requested for save at
    `changequest`, before EXP/coins exist. A map crash or kill before the
    next autosave or logout leaves the database with 18371 and **without**
    EXP/coins. After restart the tuple is state 7 → `L_Onward`. The reward is
    lost with **no debugmes**, because the in-memory readback passed before
    the crash.
  - **W2 (without `CHARSAVE_QUEST`, or quest SQL failure):** a single later
    save writes inventory and status before the quest. Partial persistence
    (inventory/status written, quest not) yields state 6 after restart, so
    **Maysel would grant again: a duplicate**. Under the default it needs a
    quest SQL failure while later inventory SQL succeeds.
  - **W3 (quest SQL partial):** `INSERT 18371` precedes `DELETE 18370`.
    - Insert OK, delete failed or interrupted → (2,-1,1,1) = state 3,
      conflict, no change.
    - Insert failed, delete OK → (2,-1,-1,-1) = state 5. Entry holds
      (`L_Interrupted`, S:npc/entry.txt:171) and Maysel shows the default
      line. No reward.

### Source-established defects and gaps (report only; nothing edited)

- **D1 (low severity, native):** `intif_parse_questsave` looks up
  `map_id2sd(cid)` with a **char ID** (P:src/map/intif.cpp:2121). `pc_db` is
  keyed by account ID (P:src/map/map.cpp:2190, 2363–2366;
  P:src/map/pc.cpp:1452). A success ACK therefore normally finds no player
  and never clears `save_quest`, so every later `chrif_save` resends the full
  quest log. Writes stay idempotent, but the quest ACK confirms nothing on the
  map side except the absence of an error line. This analysis does not
  establish whether the line is upstream or app-modified (`intif.cpp` is in
  the modified footprint).
- **G1 (story observability, not a native defect):** EXP is neither read back
  nor branch-checked. `getexp`/`pc_gainexp` give no failure signal for the
  early-return, max-level, tax or cap paths. A completed tuple with a correct
  coin delta is reported as success even when EXP was 0 or reduced.
- **G2:** a `getitem` refusal reaches `L_RewardHold`, but quest 18371 may
  already be persisted (W1). The hold is a warning plus a `debugmes` line, not
  durable quarantine. The next talk takes `L_Onward` (state 7) with no marker.

## 3. Conditional EXP expectation

The pipeline for the argument pair (B, J) = (65,304,744, 4,000,000) is below.
**Monster `base_exp_rate`/`job_exp_rate` are not applied on this path.**

1. `B1 = min(floor(B * quest_exp_rate/100), MAX_EXP)`, and the same for J
   (script.cpp:11266–11271). The default rate is 100
   (P:conf/battle/exp.conf). `MAX_EXP` depends on PACKETVER
   (P:src/config/const.hpp:64–68).
2. Guild tax on base only: `B2 = B1 - floor(B1 * exp_mode/100)` when the
   character is in a guild with position `exp_mode ≥ 1`
   (P:src/map/guild.cpp `guild_payexp`); 100 or more takes all.
3. Boosts with `src = nullptr`, so race/class/VIP-monster bonuses do not
   apply. They are `SC_EXPBOOST` (+VIP battle-manual share) and
   `SC_PERIOD_PLUSEXP_2ND` for base. Job gets `SC_JEXPBOOST` plus the same
   **accumulated** bonus (pc.cpp:8453–8478). Note the base bonus total also
   carries into the job calculation. Each result is clamped to [1, MAX_EXP].
4. Max level: at max base/job level, gain is limited so the total stays
   ≤ 99,999,999 base / 999,999,999 job (pc.cpp:8543–8554; const.hpp:73–75).
5. `max_exp_gain_rate` (default 0 = off) caps gain to a fraction of the
   current next-level requirement (8556–8569).
6. Level consumption (pc.cpp:8305–8327, 8378–8401) works in two cases:
   - `multi_level_up` off (default): each loop subtracts the threshold and
     caps the remainder at `threshold-1`. The loop continues only while the
     remainder still meets the **next** threshold, so a non-monotonic table
     could still allow more than one level.
   - `multi_level_up` on: unlimited levels up to `multi_level_up_base/job`.
   The observable EXP field is the **post-consumption remainder**, never
   `old + B`.
7. Base and job are independent. Base level-up handlers are queued before job
   EXP is added.

Source-default tables, `P:db/re/job_exp.yml`, labelled **authored/default,
not effective**:

- **3rd classes:** max base 200 (lines 573–640, 1038–1040). A Lv200 3rd class
  is at max, so base gain clamps toward 99,999,999. A large stored base EXP
  can make it 0.
- **4th classes:** max base 275. Lv200→201 needs 653,047,446 (1468), and
  B ≈ 10.0% of that, so a base level-up occurs only if stored EXP ≥ about 90%
  of the threshold.
- **4th-class job (block 2789):** JobLv1→2 needs 4,700,000, so J alone can
  trigger a job level-up early in the job. 3rd-class job is max 70; at max,
  job gain clamps to 999,999,999.
