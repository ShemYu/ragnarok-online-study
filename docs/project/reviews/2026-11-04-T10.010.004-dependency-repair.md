The changes, in the order of the brief's six requirements:

1. **fd0.** The guest runs `exec 0< /dev/null` first, before sourcing
   anything or calling apk. `step` also redirects each child's stdin from
   `/dev/null`. Scripts, triggers and signature checking stay enabled.
   - Basis: Root's actual causal pair, with descriptor numbers untraced. The
     change guarantees a valid fd0; it claims no observed syscall.
2. **Local inputs.** A new optional `plan --apk-local MANIFEST.json`
   (`apk_local=`) works in both modes.
   - Manifest format: `t10.010.004/apk-local/v1`, with exact keys
     `file/name/version/bytes/sha256` and a basename-only `file`.
   - `read_bound` reads each file safely. The final path component must not
     be a symlink, and FIFOs cannot block the open. The file must be regular
     with one link, within a size cap, unchanged during the read, and still
     the same inode at its name afterwards.
   - SHA-256, byte count and gzip magic must match.
   - Refused before any run directory is created: duplicate file, name,
     hash or JSON key; a caller `verified` flag; conflicts with the base, ABI
     or lock; an off-1.8.1 libunwind-dev.
   - Upload members use generated names: `local-<i>.apk` and `apk-local.list`.
     `LOCAL_LIST_SHA256` in `inputs.env` binds the list.
   - Without the argument, the upload member set is the same as before.
     The only change is `LOCAL_LIST_SHA256='none'` in `inputs.env`.
3. **Guest authentication.** `verify_apk` rechecks bytes and SHA-256 and runs
   real `apk --no-network verify` with the unchanged stock keys.
   - The signed `.PKGINFO` pkgname, pkgver and arch must match the expected identity.
   - The key-directory digest is recorded before and after, and must be equal.
   - All verifications precede the real transaction.
   - Never used: imported keys, `--allow-untrusted`, `--keys-dir`,
     `--no-scripts`, `--force-*`, `--arch` or `upgrade`.
4. **Solver constraints.** The solver receives every frozen base pin, WANT
   (`libunwind-dev~1.8.1`), the exact delta pins (build mode) and the local
   files, in both `add --simulate` and the real `add`.
   - Any simulated transaction other than `Installing` refuses before
     anything is installed. So does a solver failure.
   - In build mode, the simulated delta must equal the lock.
   - The previous before/after equality and exact-delta checks are retained.
5. **Closure retention.** Repository additions are fetched individually into
   generated directories, which must each yield exactly one regular file.
   Each file is then authenticated.
   - One `--no-network --repositories-file /dev/null` transaction installs
     from exactly those files.
   - Resolve exports retain every delta file's bytes and `apk-closure.txt`.
   - They also retain `MANIFEST.json` in the `--apk-local` format, and the
     installed-database `C:` identities.
   - Base packages are not refetched.
   - A build whose manifest covers the full delta plans
     `apk_package_network: false`, and its guest runs offline. **The source
     supports this, but it has not been exercised.**
6. **Export join.** `check_dependency_evidence` joins all of these against
   each other:
   - base-current against base-candidate, or the plan's base
   - the solver delta against the lock candidate, or the plan's lock
   - the before and after names and versions
   - the exact added set
   - the trusted keys
   - the installed identities
   - each closure entry's verification (tag, full hash, identity, arch, OK)
   - the local inputs against the plan
   - the retained bytes and MANIFEST.json against the closure

   Contradictory exports fail even when their checksums are coherent.
   Resolve output remains `candidate only`.

### What changed

The changes are in the same allowed files.

- **Parser.** `apk_identity()` is a bounded APK v2 parser:
  - Gzip member 1 must hold only signature entries. Member 2 is the control
    member. A data member must follow, and it is never inflated.
  - Tar checksums are verified. Local PAX headers may carry time-only
    records, which is what the actual files use.
  - The parse yields name, version, arch, datahash and
    `Q1 = Base64(SHA1(compressed control member))`.
  - Unsupported, truncated, corrupt and ambiguous layouts refuse.
  - Basis: `extract_v2.c` `apk_sign_ctx_mpart_cb` digests the compressed
    `APK_MPART_DATA` of the control member into `identity_ctx`. `blob.c`
    `apk_blob_push_hash` writes `Q1` + Base64. `package.c` writes it as `C:`.
- **Plan.** Local manifests now require derived identity = claim and
  arch = `aarch64`. The plan and the guest list record each Q1.
- **Guest.**
  - The installed `C:` of each local input must equal its planned Q1.
  - Build mode now also retains fetched repository bytes. Its local bytes
    are joined from the plan's upload.
  - Authentication is unchanged: real stock-key `apk verify` runs before install.
- **Validator, resolve and build.**
  - Every closure entry's raw bytes are parsed. Derived name=version, arch
    and Q1 must equal the claimed entry, the plan and the installed `C:`.
  - Build-mode local bytes come from `upload.tar`, after its SHA-256 is
    checked against the plan.
  - This also covers the complete offline input path.

Unchanged: all 26 base pins and their solver constraints, WANT, ABI,
crash-trace flags, the fd0 fix, exact delta checks, the Engine lifecycle,
and the source, patch and profile pins.

## Repair 3: actual APK transaction-counter format

**Inputs.** Besides the [repair-3 brief](../tasks/T10.010.004-dependency-repair-3.md),

  rows padded to width 2 and then `OK:`
- `apk-counter-format-root-1/RESULT_ROOT.json` (`21adbf53…06d2`)

These are diagnostics from a failed guest. There is no guest PASS, no
SHA256SUMS and no qualified closure, and this repair does not change that.

**Defect.** I reproduced Root's finding. My parser recognised only
`^\([0-9]+/[0-9]+\) `. Padded rows 1–9 therefore matched nothing and were
dropped silently: 38 of 47 rows, so binutils was missing. For the same
reason, a padded `Upgrading` row was ignored rather than refused.

**Change.** The only source change is `parse_simulate` in `guest_lib.sh`. It
now applies a strict grammar to every line that starts with `(` or names a
transaction action:

- The counter may be unpadded or space-padded to exactly the total's width.
- Counters run 1..n in order, with one constant total and exactly n rows.
- The action must be `Installing`, with a valid name and `(version-rN)`, and names must be unique.
- Everything else refuses before any fetch or install.

The transaction contract and every other requirement are unchanged. The
modelled solver in the tests now pads counters as the real log does.

### Repair 3 follow-up: indented transaction rows

Root reviewed `90365e35` (coordinator `2715851`, "Captured-format candidate
review"; host control `apk-counter-format-root-2/RESULT_ROOT.json`, SHA-256
`69f05d46…4210b`). With that parser, appending ` (48/47) Frobbing zlib

bare `(`. The fix is one rule in `parse_simulate`: a line matching

- the indented unknown row appended to a valid plan (Root's case)
- an indented row that is otherwise a valid Installing row
- a tab-indented Upgrading row
- an indented malformed counter
- in the private replay, Root's exact appended row on the actual log, which now refuses

Removing the new rule makes Root's case fail again; the other indented cases
are also caught by existing rules.

**Source finding.** The failure was a query-semantics problem; it is not
evidence that the package is missing.

- `apk_query_matches`:
  - It defaults `qs->match` to `BIT(APK_Q_FIELD_NAME)` and sets
    `m.match = arg`, so `acl-libs=2.3.2-r1` is kept whole.
  - `apk_dep_parse` gives `m.q = bname`.
  - The exact-NAME fast path then calls `match_name()`, which compares
    `name->name` (`acl-libs`) with `m->match` (the whole argument). The
    comparison fails, so the function returns before any provider or
    version check.
- `fetch_match_package` then prints exactly Root's message.

With `--match package` (the fetch applet enables the query option group):

- The argument `acl-libs-2.3.2-r1` contains no comparer. `apk_dep_parse`
  keeps it whole, and match mode is `EXACT`.
- Because the match is not NAME-only, the code takes the full
  `apk_hash_foreach` scan.
- `qs_nonindex.fields` is PACKAGE, so `__apk_package_serialize` emits
  `pkgser_serialize_package`, which is the `PKG_VER_FMT` name-version string.
- `ser_match_string` compares that string exactly via `match_blob` and
  calls `update_best_match`. Only exact matches reach the callback.
- `fetch_main` downloads nothing if any argument is unmatched.
- The recursive path runs only with `-R`/`--world`, so this path never
  downloads dependencies.

**Change (only `guest_lib.sh` deps_transaction changed).** The per-package
`name=version` loop is replaced by:

- one batched `apk fetch --no-cache --match package --output <fresh empty dir> name-version…` call;
- then a set of gates that apply whatever the exit status:
  - Total entries must equal the wanted count.
  - The same count must be regular, non-hidden `*.apk` files.
  - Each file is mapped by its signed `.PKGINFO` pkgname/pkgver, and an
    unrequested identity refuses.
  - The sorted mapped set must equal the wanted set (with equal counts,
    a duplicate implies a missing package).
  - Each file is renamed `repo-K.apk` in delta order and re-authenticated
    with `verify_apk` (real stock-key verify plus signed identity).

Everything else is unchanged:

- the 26 base constraints and the strict padded/indented/uncounted transaction parser
- local authentication, the single offline install from exactly the
  authenticated files, and the installed `C:` joins
- the host raw N/V/A/Q1/full-hash validation (metadata-only; no payload inflation)
- the lifecycle and the 600 s resolver bound

**Tests (`FetchSelectionTests`, plus updated existing tests).** The
modelled apk `fetch` follows the pinned selection semantics: default name
matching never selects `name=version`, `--match package` compares
`name-version` exactly, and any miss downloads nothing.

- **Old call versus new call:**
  - The old call refuses with Root's exact message.
  - The exact package field succeeds.
  - A wrong version, a bare name, or one missing package in a batch downloads nothing.
- **Batched call:**
  - The batch includes hyphenated names (acl-libs, git-init-template,
    libstdc++-dev, mariadb-connector-c-dev, zstd-libs).
  - There is exactly one fetch, with no `=`, wildcard or `-R`.
  - Every repository verify falls between the fetch and the single add.
- **Refusals before any add, with fetch exit 0:** missing file, extra file,
  wrong package bytes, duplicate identity, hidden entry, symlink,
  subdirectory, non-`.apk` name, failed signature.
- **No fallback:** an unavailable exact version refuses even when another
  version exists, with no retry.
- **Forbidden plans refuse before fetch:** padded Upgrading, indented
  unknown, and uncounted Upgrading.
