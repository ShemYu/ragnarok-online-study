The changes, in the order of the brief's six requirements:

1. **fd0.** The guest runs `exec 0< /dev/null` first, before sourcing
   anything or calling apk. `step` also redirects each child's stdin from
   `/dev/null`. Scripts, triggers and signature checking stay enabled.
   - Basis: Root's actual causal pair, with descriptor numbers untraced. The
     change guarantees a valid fd0; it claims no observed syscall.
2. **Local inputs.** A new optional `plan --apk-local MANIFEST.json`
   (`apk_local=`) works in both modes.
   - Manifest format: `t10.010.004/apk-local/v1`, with exact keys
     `file/name/version/bytes/sha256` and a basename-only `file`.
   - `read_bound` reads each file safely. The final path component must not
     be a symlink, and FIFOs cannot block the open. The file must be regular
     with one link, within a size cap, unchanged during the read, and still
     the same inode at its name afterwards.
   - SHA-256, byte count and gzip magic must match.
   - Refused before any run directory is created: duplicate file, name,
     hash or JSON key; a caller `verified` flag; conflicts with the base, ABI
     or lock; an off-1.8.1 libunwind-dev.
   - Upload members use generated names: `local-<i>.apk` and `apk-local.list`.
     `LOCAL_LIST_SHA256` in `inputs.env` binds the list.
   - Without the argument, the upload member set is the same as before.
     The only change is `LOCAL_LIST_SHA256='none'` in `inputs.env`.
3. **Guest authentication.** `verify_apk` rechecks bytes and SHA-256 and runs
   real `apk --no-network verify` with the unchanged stock keys.
   - The signed `.PKGINFO` pkgname, pkgver and arch must match the expected identity.
   - The key-directory digest is recorded before and after, and must be equal.
   - All verifications precede the real transaction.
   - Never used: imported keys, `--allow-untrusted`, `--keys-dir`,
     `--no-scripts`, `--force-*`, `--arch` or `upgrade`.
4. **Solver constraints.** The solver receives every frozen base pin, WANT
   (`libunwind-dev~1.8.1`), the exact delta pins (build mode) and the local
   files, in both `add --simulate` and the real `add`.
   - Any simulated transaction other than `Installing` refuses before
     anything is installed. So does a solver failure.
   - In build mode, the simulated delta must equal the lock.
   - The previous before/after equality and exact-delta checks are retained.
5. **Closure retention.** Repository additions are fetched individually into
   generated directories, which must each yield exactly one regular file.
   Each file is then authenticated.
   - One `--no-network --repositories-file /dev/null` transaction installs
     from exactly those files.
   - Resolve exports retain every delta file's bytes and `apk-closure.txt`.
   - They also retain `MANIFEST.json` in the `--apk-local` format, and the
     installed-database `C:` identities.
   - Base packages are not refetched.
   - A build whose manifest covers the full delta plans
     `apk_package_network: false`, and its guest runs offline. **The source
     supports this, but it has not been exercised.**
6. **Export join.** `check_dependency_evidence` joins all of these against
   each other:
   - base-current against base-candidate, or the plan's base
   - the solver delta against the lock candidate, or the plan's lock
   - the before and after names and versions
   - the exact added set
   - the trusted keys
   - the installed identities
   - each closure entry's verification (tag, full hash, identity, arch, OK)
   - the local inputs against the plan
   - the retained bytes and MANIFEST.json against the closure

   Contradictory exports fail even when their checksums are coherent.
   Resolve output remains `candidate only`.

## Limitations

- These real formats are assumed, unobserved, and each fails closed if wrong:
  - the `verify` OK text
  - `--simulate` "(i/n) Installing name (version)" lines
  - `fetch --output` producing one file
  - installing signed files given as arguments without `--allow-untrusted`
  - BusyBox `tar -xzOf` over multi-member APK v2 files
  - installed-db `C:`/`P:`/`V:` records
- Exact base pins are added to `/etc/apk/world`. Installed versions must stay
  unchanged; the world file is not required to.
- The current repository may still require newer base libraries for other
  additions, such as the mariadb-dev or openssl closure. This recipe then
  refuses; it does not upgrade. Whether the three local development APKs
  are enough is unknown until Root runs it.
- Resolve still needs container networking for the index and fetches.
  Per-package fetch reloads the index each time, which is bounded by
  `STEP_TIMEOUT` per step.
- Build-mode exports record the closure hashes but do not re-export bytes.
  The qualified bytes are the resolve export's retained closure.
- Model: `claude-opus-5-5` as configured; the provider-reported model was
  not observed. Cost and tokens were not observed.

### What changed

The changes are in the same allowed files.

- **Parser.** `apk_identity()` is a bounded APK v2 parser:
  - Gzip member 1 must hold only signature entries. Member 2 is the control
    member. A data member must follow, and it is never inflated.
  - Tar checksums are verified. Local PAX headers may carry time-only
    records, which is what the actual files use.
  - The parse yields name, version, arch, datahash and
    `Q1 = Base64(SHA1(compressed control member))`.
  - Unsupported, truncated, corrupt and ambiguous layouts refuse.
  - Basis: `extract_v2.c` `apk_sign_ctx_mpart_cb` digests the compressed
    `APK_MPART_DATA` of the control member into `identity_ctx`. `blob.c`
    `apk_blob_push_hash` writes `Q1` + Base64. `package.c` writes it as `C:`.
- **Plan.** Local manifests now require derived identity = claim and
  arch = `aarch64`. The plan and the guest list record each Q1.
- **Guest.**
  - The installed `C:` of each local input must equal its planned Q1.
  - Build mode now also retains fetched repository bytes. Its local bytes
    are joined from the plan's upload.
  - Authentication is unchanged: real stock-key `apk verify` runs before install.
- **Validator, resolve and build.**
  - Every closure entry's raw bytes are parsed. Derived name=version, arch
    and Q1 must equal the claimed entry, the plan and the installed `C:`.
  - Build-mode local bytes come from `upload.tar`, after its SHA-256 is
    checked against the plan.
  - This also covers the complete offline input path.

Unchanged: all 26 base pins and their solver constraints, WANT, ABI,
crash-trace flags, the fd0 fix, exact delta checks, the Engine lifecycle,
and the source, patch and profile pins.

### Repair-2 limitations

- Identity parsing supports only the layout described above: APK v2,
  signature member, control member, then data. This matches the four
  retained files and the synthetic fixtures. APK v3 (ADB) and other layouts
  refuse. No wider format support is claimed.
- Repository files fetched in a real resolve are parsed only by the host,
  after export. The guest's pre-install check for them remains the signed
  `.PKGINFO` comparison plus real `apk verify`.
- The modelled apk writes `C:` from host-derived identities. The format of
  the real apk-tools 3.0.8 installed DB is still unobserved here.
